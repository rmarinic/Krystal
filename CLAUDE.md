# CLAUDE.md — Krystal

## Overview
- **Krystal** is a native Windows desktop chat application for **Claude Code** — it wraps the `claude` CLI in a clean graphical UI so users get a proper app experience instead of the terminal.
- **Stack:** Tauri 2 — Rust backend in `src-tauri/` + vanilla HTML/CSS/JS frontend in `src/`. No framework, no bundler.
- **Audience/goal:** make Claude Code pleasant for everyone, including non-technical users. Originally single-purpose; now being generalized to support **any** project type (writing / research / code / data).
- **Status:** functional and shipping (current version in `src-tauri/tauri.conf.json`); releases automated via GitHub Actions.

## Architecture (keep this split)
- `src-tauri/src/claude/` — finds and installs the CLI, builds its invocation, and turns its stream-json output into UI events, **one file per concern**: `binary` (resolving `claude`, `Caps`, process-tree kill), `auth` (signed in? + in-app sign-in), `install` (install/update/npm fallback), `args` (flags, mode, system-prompt spill, `claude_command`), `prompt` (the system prompt and `build_prompt`), `permissions` (`handle_control`, `is_own_business`), `orchestration`, `tools` (chip detail/diff/output), `ask` (the ```` ```krystal-ask ```` choice-card parser), `turn` (`ChatResult`, `TurnRequest`, `run_turn`), `agents` (`BackgroundAgents`, the agent inspector's events), `events` (`TurnState`: every event of a turn goes through `route`, which hands it to one handler per event kind — a new CLI event type gets its own `on_…` method there), `oneshot` (titles, `run_claude_text*`, the `$` shell), and `limits` (the plan's usage limits: the usage endpoint behind the CLI's `/usage`, and each turn's `rate_limit_event`, normalised to one list of windows). `mod.rs` re-exports them, so callers still write `claude::foo`. `base_args` + `apply_mode` + `apply_chat_flags` + `apply_session_flags` assemble the flags: the system prompt spilled to a file, `--effort`, `--fallback-model` (an overloaded model degrades instead of failing the turn), `--autocompact auto`, `--add-dir` for each folder the project has been granted beyond its own, `--mcp-config` for the artifact tool (see `artifacts.rs`; deliberately *not* `--strict-mcp-config`, which would switch off the user's own MCP servers), and in orchestrator mode the worker sub-agents defined inline via `--agents`. `build_prompt` assembles the turn's message: background context (task note, compact seed, #-referenced chats, attached files) leads — **except** when the message opens with `/skill-name`, which the CLI only resolves at the very head of a prompt, so those messages lead and their background follows. `run_turn` drives one turn on a warm session and ends at its `result` event — **unless a background sub-agent is still out** (`BackgroundAgents`): the CLI emits a `result` as soon as Claude says "I'll report back", then wakes itself when the agent finishes and answers again with a second `result`, so the turn is held open until that one. The agent's report arrives as a `task_notification`, not as the result of the call that launched it. `--forward-subagent-text` plus the sub-agent's own `tool_result`s (tagged `parent_tool_use_id`) feed the agent inspector's timeline.
- **Modes** (`models::MODES`, applied by `claude::apply_mode`): **Full access** (id `auto` — what every older chat has stored) keeps `--dangerously-skip-permissions`; **Auto** (id `guarded`) is Claude Code's own `--permission-mode auto`, where a classifier checks each action instead of the user; **Accept edits** (id `edits`) is `acceptEdits`; **Plan** swaps it for `--permission-mode plan`; **Ask** is the terminal's own behaviour — `--permission-mode default` plus `--permission-prompt-tool stdio`, which makes the CLI hand each permission prompt to its *host* instead of refusing (headless, it has nobody else to ask). A prompt arrives as a `control_request`/`can_use_tool` on stdout; `claude::handle_control` parks it on the session and emits a `permission` event, and `commands::answer_permission` writes the `control_response` on stdin (`allow`, `always` = allow and hand the CLI's own `permission_suggestions` back as `updatedPermissions`, or `deny`). The CLI still decides *what* needs asking, so the user's own rules in `.claude/settings*.json` apply as they do in a terminal. Prompts about Krystal's own plumbing — the artifact tool, the task snapshot, saved attachments — are answered by `claude::is_own_business` and never reach the user. Auto and Accept edits get the same host-answered prompt as Ask, for whatever they don't wave through. Ask mode gates each use on a yes; it does **not** curate the toolset.
- `src-tauri/artifacts.rs` — **artifacts**: the self-contained documents Claude builds (a page, a drawing, a report) that open in a panel beside the conversation instead of as a code block inside it. The `claude` binary has no Artifact tool of its own — that is something the *host* application provides — so Krystal hands the session one, over MCP (`--mcp-config`), and it appears in the toolset as `mcp__krystal__artifact`. The MCP server is **this same executable** re-launched with `MCP_FLAG` (`--krystal-mcp-artifacts`), speaking JSON-RPC on stdio; `claude` starts it, Krystal never talks to it. It is the only thing that applies an `old_str`/`new_str` patch, and it writes the resolved document under `KRYSTAL_ARTIFACT_DIR`. Krystal picks the content up from the `tool_use`/`tool_result` events `claude/events.rs` already parses, so there is one implementation of the patch logic and no IPC bridge to a grandchild process. The content never travels back through the tool's *result* — that would re-inject the whole document into Claude's context on every revision.
- `src-tauri/src/session/` — **persistent per-chat `claude` processes** (`mod.rs`: `Session`; `control`: the control-protocol messages and `track_agents`; `pool`: `Pool` and eviction). A chat is served by one `--input-format stream-json` process: each message is a JSON line on its stdin, so the session id, the loaded context and the prompt cache survive between turns instead of being rebuilt with `--resume` every time. Everything passed as a flag is fixed at spawn, so the flags form the session **key** — changing model/mode/effort/orchestrator (or compacting, clearing, moving the project) retires the process and the next message starts a fresh one. Stop is two-step: the first press is a `control_request`/`interrupt`, not a kill, so a stopped turn keeps its session — but an interrupt is only a *request*, and a turn wedged in a tool run may never honour it, so a second press (or the frontend's escalation timer) makes `stop_chat` retire the session and kill the process tree. An interrupt also never reaches a **background sub-agent**, which lives on in the warm process after its turn ends. So the stdout reader tracks the live agents (`track_agents`), and a stop that finds one goes straight to the kill. `stop_task` does stop a single agent, but the CLI then wakes Claude to answer about it with nobody reading, and that stray `result` would end the chat's next turn early. `Pool` caps warm sessions (`MAX_WARM_SESSIONS`) and retires idle ones (`IDLE_TIMEOUT_SECS`); everything is retired on app exit.
- **Undoing a turn's file changes** (`commands::rewind_files` → `Session::rewind_files`) rides on the CLI's own file checkpointing rather than a snapshot store of ours: sessions are spawned with `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1`, every user message is sent with a `uuid` of our choosing (saved as `messages.ckpt`), and a `control_request`/`rewind_files` naming that uuid puts the project's files back to how they were before that message (`dry_run` only reports). It works on a resumed session too, so a retired process is no obstacle — but checkpoints belong to the session, so a cleared/compacted chat can't be rewound past that point, and only what Claude's *file tools* changed is covered (not a file a shell command rewrote). `commands::session_setup` is the one place a chat's spawn args are built, because those args are the session key and both a turn and a rewind need the same process. The conversation is left alone; `Pool::leave_note` tells Claude on the next message.
- **Per-turn context can't go in the system prompt** — that's fixed at spawn. Anything that varies per turn (today: the task-list note) rides on the user message via `claude::build_prompt`'s `notes` argument.
- `src-tauri/src/commands/` — Tauri command handlers exposed to the frontend, **one file per concern**: `config` (language, models, suggestions, Discord), `setup` (preflight, install/update, sign-in), `system` (notifications, links, in-app browser, Show in folder / Open), `attachments`, `threads` (chats, per-chat settings, search/favourites, compact), `projects` (picker, move, extra folders, skills, CLAUDE.md check), `turn` (`chat`/`chat_turn`, `session_setup`, rewind, #-references), `running` (stop, permissions, active runs), `tasks` (CRUD, generation, the task snapshot), `git`, `ci` (GitHub Actions via `gh`), `usage`, `run` (`$` shell + RUN button), `wizard` (Initialize + CLAUDE.md editor), `pins`, `artifact_panel`, and `json` (`--json-schema` + `extract_json`, the safety net for one-off calls whose reply is parsed as JSON). `mod.rs` holds `AppState` and `pub use`s every file, so callers still write `commands::foo` and `generate_handler!` is unchanged; a helper one file lends another is `pub(super)`. A new command goes in the file that owns its concern — don't grow `mod.rs`. `AppState::db()` is how a command gets the connection (it survives a poisoned lock).
- **Adding a backend command** touches four places that only agree by convention: the `#[tauri::command]` fn, its entry in `main.rs`'s `generate_handler!`, either a `dispatch` arm in `remote/bridge.rs` (so a caller from outside — the Krystal Cloud relay — can reach it; it reads each argument by its camelCase name) or an entry in `LOCAL_ONLY` right beside it (commands that act on the machine you're sitting at, or that hand out access, like `cloud_*`), and the `invoke('cmd', { … })` call (in `api.js`). `tests/commands.test.js` reads all four and fails on any mismatch.
- `src-tauri/src/util.rs` — the few helpers more than one module needs (`base_name`, `exe_path`). A helper only one module uses stays in that module.
- `src-tauri/src/db/` — SQLite persistence for chats/projects, **one file per concern**: `mod.rs` (schema, `open`, migrations, `now`), `threads` (metadata, listing, per-chat settings), `turns` (the three beats below, compaction, `$` runs), `branch`, `messages` (search, favourites, delete), `projects` (incl. extra folders and `move_project`), `tasks`, `run_config`, `pins`, `artifacts`. `mod.rs` re-exports them, so callers still write `db::foo`; its `mod tests` covers them all. A turn is written in three beats rather than one, so nothing is lost if the app goes away mid-answer: `begin_turn` saves the user's message *before* Claude is asked anything (and gives an unnamed chat its fallback title there and then), `save_partial` re-writes the answer as it streams (throttled by `claude::PARTIAL_SAVE_MS`), and `finish_turn` completes those same rows and rolls up the totals. A turn that produced nothing (stopped early, session refused to start) ends at `abort_turn`, which keeps the message and drops the empty answer. Rows carry a `partial` flag while the turn is in flight — one left set is a turn the app never finished, and the UI badges it as interrupted.
- `src-tauri/src/remote/` — **commands reachable from outside the window**, with no transport of its own (`mod.rs`: the mirror events and the tests; `bridge`: `dispatch` and `LOCAL_ONLY`; `stream`: a chat turn or the RUN button as a stream of events). Its carrier, the Krystal Cloud relay (`cloud/relay.rs`), hands it a command name plus JSON arguments and gets JSON back (`dispatch`, an explicit allowlist calling the *same* command functions the window invokes, so whatever drives this machine from elsewhere is a second view of one app, not a second app), or for a turn an `mpsc` receiver of the JSON events the window's own Channel would have got, closing with `{"type":"end"}` / `{"type":"error"}` (`stream`, built by handing `commands::chat` a `Channel::new` whose handler feeds the queue). The same events are mirrored to the desktop window (`remote-turn-start` → `remote-turn` per event → `remote-turn-end`, all carrying one `turn` id; replayed by `mirror.js`) so an open chat paints a turn from outside live, and a chat created through `dispatch` nudges the sidebar (`remote-threads-changed`). The end event, not `done`, is where a mirrored turn's story stops: the first reply's real title arrives *after* `done`. A RUN started from outside is not mirrored (the window's run modal only follows runs it started). Generic over the Tauri runtime so it runs against a mock app in its tests (`remote::tests::mock_app`, which the relay's tests borrow). **There is no listener**: the LAN server (hyper on `0.0.0.0:7420`, PIN pairing, the firewall row) and the phone UI it served (`src-tauri/src/webui/`) are gone; the end of `CHANGELOG.md` names the last commit that has them.
- `src-tauri/src/cloud/` — **Krystal Cloud, the desktop's half** (`mod.rs`: the `cloud_*` commands, `machine_name`, the `cloud-link` and `cloud-presence` events; `api`: the `Net` seam and its reqwest implementation; `link`: the link state machine; `presence`: the live connection; `relay`: the relay over it; `wire`: its WebSocket seam (`Wire`/`Socket`) and the tokio-tungstenite implementation; `vault`: the token in Windows Credential Manager via `keyring`; `fakes`, test-only: the scripted `Wire`, the fake socket whose far end a test plays as the cloud, the fake account and the `Rig` that `presence`'s and `relay`'s tests share). Linking is a device-code flow: `POST /api/link/start` → a code shown in Settings → Remote → Account and a poll secret that never leaves `link.rs` (anyone can see the code, so the code alone must not claim the token); nothing opens by itself: the code is entered at app.krystal.rip once signed in, and the panel's "Open app.krystal.rip" (`Link::open_site`) opens the site; `poll_until_done` polls `POST /api/link/poll` every `interval` (5 s longer after each `429 slow-down`, three unreachable polls in a row = offline, `410` = expired) until approved / denied / expired / cancelled. `check` (`GET /api/device`, on launch and when the Account tab is on screen) treats a 401 as "unlinked at app.krystal.rip": forget the token, say so. `unlink` forgets the token first and tells the cloud second. **Every call is made from Rust, never the webview** (the Worker refuses a state-changing request with a foreign `Origin`, and the token must never reach JavaScript); the window only ever sees `Link::status()` = `{ state, linked, email, deviceName, code, problem }`. Base URL `https://app.krystal.rip`, or `KRYSTAL_CLOUD_URL` (e.g. `http://localhost:8787` for `wrangler dev`); the credential is keyed by base URL so a dev link never clobbers the real one. The cloud side is `../krystal-cloud` (`worker/link.js`, `worker/devices.js`); the contract lives in the `krystal-cloud-plan` artifact. `link.rs`'s tests run the whole state machine on a scripted fake `Net` in virtual time.
- **Presence** (`cloud/presence.rs`) implements `../krystal-cloud/PROTOCOL.md` (protocol v2, cloud end `worker/relay.js`) exactly; change it only together with that document. The hello says `apiVersion: 2` (`link::API_VERSION`, the same number `/api/link/start` gets): presence plus the relay. A cloud that welcomes at 1 gets presence only. While linked and **"Reachable from krystal.rip"** is on (Settings → Remote → Account; on unless turned off, remembered as an off-mark file in the app data folder so it holds before the window loads), one outgoing WebSocket (`wire.rs`: tokio-tungstenite, rustls) to `/device` with the device token as bearer: `hello` → `welcome` (online; its `name` goes to `Link::named`) → the exact bytes `{"type":"ping"}` every `heartbeat` seconds, dead if no pong in 10 s → reconnect with backoff 1 s … 60 s ±20%, reset after a minute up. A `401` at the handshake or a `4401` close calls `Link::revoked`, the same path as `check`'s 401 (forget the token, Not linked, `unlinkedRemotely`), and never redials; `4409` (another Krystal has the token) and `4426` (update) park it until the switch is flipped. It follows `Link::key()` (a `watch` of the token), so linking opens it, unlinking closes it with `1000`, and so does quitting (`shutdown` from the exit handler). `KRYSTAL_CLOUD_URL` applies (`http`→`ws`). The window sees only `{ reachable, conn }`. Tests drive the same loop on a fake socket in paused tokio time, plus the real adapter against a local WebSocket server. This socket is also what the relay rides, which is why there is no separate heartbeat for remote streams.
- **The relay** (`cloud/relay.rs`) implements `PROTOCOL.md`'s "Relaying (apiVersion 2)" exactly (cloud end `worker/frames.js`; the welcome brings `window` and `maxFrame`); change it only together with that document. Someone signed in at app.krystal.rip drives this computer: the cloud sends `{"type":"call"|"stream", id, command, args, from}` down the socket, presence's loop hands every non-presence message to the connection's `Relay` (made from the welcome, dropped with the socket), and what the relay has to say goes into an outbox the same loop drains, after the heartbeat in its `select!` so a busy stream never delays a ping. A `call` runs `remote::dispatch` and answers once: `{"type":"result", id, ok: true, value}`, or `ok: false` with a `code`: `failed` (the command's `Err`, in `error`) or `not-allowed` (not exposed). A `stream` runs `remote::stream` and answers with `{"type":"events", id, events: [...], end}` frames, in order, the last `end: true` (the stream's own `{"type":"end"}`/`{"type":"error"}` is inside it); refused before it began (busy, a missing argument) it gets one `result` with `code: "refused"`. Every frame wakes the cloud and is billed, so events are **batched**: a frame goes once its oldest event is `BATCH_AFTER` (50 ms) old, once it holds `BATCH_BYTES` (64 KiB), or when the stream ends. At most `window` `events` frames of a stream are unacknowledged (`{"type":"ack", id, frames}` is a running count); events that arrive meanwhile wait and go out together. A frame over `maxFrame` goes as `{"type":"part", id, data, last}` pieces of at most `PART_BYTES` (256 KiB) of its text, each within `maxFrame` once escaped. Not done yet: the protocol's optional `watch_turn { threadId }` stream (a phone that slept coming back to a running turn); until it exists it answers `not-allowed` and the web app re-reads the chat instead. `{"type":"cancel", id}` (the browser went away) stops the sending only: the turn goes on (stopping it is the `stop_chat` call) and a call runs to its end with its answer dropped. A socket that goes takes its streams with it; the turns go on. **`LOCAL_ONLY` has two doors**: the relay refuses it before `remote` is asked, and `dispatch`/`stream` have no arm for it; a streaming command sent as a `call` is refused too. `from` (who asked, and whether they own the computer) is not acted on yet: the cloud has already checked access. The handler is a seam (`relay::Handler`; the app's is `AppHandler`, set by `cloud::start_presence` through `Presence::serve`), so the tests run the relay through presence's real loop on the fake socket with a fake handler, and once end to end with the mock app: a call answered from its database, a turn's events up the socket and the same events in the window.
- `src-tauri/src/legacy.rs` — tidying up after features that are gone: on launch, delete the old LAN server's "Krystal Remote" firewall rule if it's there. That needs admin: the quiet delete is tried first (works on an elevated launch), and if Windows refuses, Krystal asks **once** — one UAC prompt for `netsh`, run as `-EncodedCommand` so nothing has to be quoted twice. Either way a mark in the app data folder stops it ever looking again.
- **The web lives in two sibling repos:** the public site **krystal.rip** in `../krystal-site`, and **Krystal Cloud (app.krystal.rip)** in `../krystal-cloud` (plan in the `krystal-cloud-plan` artifact): accounts, linked computers, presence and a relay so a phone reaches any of your computers from anywhere. This repo only gets the desktop's half of it: linking this computer (`cloud/link.rs`, done), the outgoing connection that keeps it online (`cloud/presence.rs`, done), the relay that rides it (`cloud/relay.rs`, done), and the Account section of Settings → Remote. Decided and done: no tunnels and no direct LAN access. The LAN server and the phone UI are removed, and a phone reaches a computer only through the cloud.
- `src/app/` — the frontend UI logic, split into cohesive **classic scripts that share one global scope** (no bundler/modules). They load in order via `<script defer>` (see `index.html`); a symbol declared in an earlier file is visible to all later ones, so **load order matters** and `boot.js` (the entry point) loads last. `tests/boot.test.js` loads every script in `index.html`'s order against a stub DOM and fails on a load-time `ReferenceError` — the way a moved or split file breaks. When splitting a file, cut contiguous ranges and load the new files where the original was, so the code still runs in the same order. Layout: `core` (IPC + the wire/`els`/`state`) → `api` → `utils` → `lightbox` → `icons` → `motion` → `light` → `mascot` → `titlebar` → `sidebar` → `chat` → `projects` → `starters` → `controls` → `describe` → `activity` → `agents` → `search` → `messages` → `review` → `artifacts` → `livemd` → `composer` → `feed` → `working` → `typer` → `stream` → `permissions` → `mentions` → `skills` → `attachments` → `queue` → `wizard` → `localization` → `settings` → `header` → `tasks` → `git` → `run` → `links` → `logo` → `usage` → `orchestrator` → `pins` → `mirror` → `account` → `notifications` → `palette` → `find` → `hotkeys` → `boot`. See `src/app/core.js` for the full map.
- `src/i18n.js`, `src/onboarding.js`, `src/updater.js` — i18n dictionary, first-run onboarding, and self-update (load before the `app/` modules).
- Self-updates ship via **GitHub Releases**.

## Frontend file map (where to find things)
Loaded in this order; each file may use symbols from any earlier one (shared global scope).
- `src/i18n.js` — EN/HR string dictionary + `window.I18N` (`t`/`getLang`/`setLang`); fires `i18n:changed`.
- `src/onboarding.js` — first-run gate: install Claude Code + sign-in flow (own IIFE scope).
- `src/worklight.js` — the **work light** behind every full-screen wait (Compact / Clear / Update Claude Code in the proc overlay, and the self-update): the bar moves with real progress (the summary's characters — `compact_thread` streams them via `claude::run_claude_text_live` — or the download's bytes) and only creeps on time before any arrives; the light behind the icon and at the bar's edge brightens on each real event and cools slowly. Pure step `workStep`, tested in `tests/worklight.test.js`. Loads before `updater.js`, which uses it.
- `src/updater.js` — self-update overlay (check GitHub Releases, download, install).
- `src/app/core.js` — foundation: Tauri IPC handles (`invoke`, `Channel`, `listen`), `$`, `tr`, the `els` element map, `state`, context-window constants.
- `src/app/api.js` — the `api` wrapper, one method per backend command.
- `src/app/utils.js` — shared helpers (`basename`, `escapeHtml`, `closeOverlay`/`openOverlay`, `replayClass`, time/day labels, `renderMarkdown`, copy buttons, `decorateCode`, `isShellTool`/`shellPrompt`, …).
- `src/app/lightbox.js` — click any image thumbnail to see it full-size.
- **Look:** text is Inter, mono (JetBrains Mono) only for what is genuinely technical — code, paths, numbers, the ▸ prompt, the box-art logo. Both ship in `src/fonts/` (SIL OFL, licences alongside) with `@font-face` in `css/base.css`; nothing is fetched from the network. Surfaces are separated by tone and soft shadow rather than 1px borders; the reading column is `--read-w` (css/base.css), shared by the transcript and the composer dock. Your messages are compact bubbles on the right; Claude's replies sit on the page with no card.
- `src/css/` — **the stylesheets**, linked one by one in `index.html`: `base.css` (variables, fonts, the base look) first, `motion.css` (the motion layer) last, and between them one file per part of the window, mostly named after the module that draws it (`sidebar`, `transcript`, `composer`, `header`, `activity`, `agents`, `review`, `tasks`, `settings`, `git`, `projects`, `pins`, `account`, `artifacts`, `notifications`, `palette`, `titlebar`, `starters`, …). **The link order is the cascade**: a later file wins a tie, so a rule moved between files can change what wins — style a feature in its own file, and add a new file's `<link>` where it belongs rather than at the end by habit. Paths inside a stylesheet are relative to `src/css/` (fonts are `../fonts/`).
- `src/app/icons.js` — **the one icon set** (line icons, one stroke weight, `ICON_PATHS`). `icon('name')` gives an inline `<svg class="ui-ico">` for markup built in JS; `data-icon="name"` on any element draws the same icon as a CSS mask in its `::before` — for elements whose text `data-i18n` rewrites (that would wipe an inline svg). The mask rules are generated from the same paths at load. **No emoji in the UI** (Windows draws them in its own style); tips take an icon *name* (`showTip({ icon: 'alert' })`, rendered through `iconOrText`).
- `src/app/header.js` — the chat header's **⋯ menu** (Edit instructions, Settings, Language) and the **context ring** at the end of the dock's tools: `updateUsage` (chat.js) fills the same `#meter-fill`/`#meter-label` — now inside the ring's popover, with the usage chip — and calls `paintContextRing(pct, level)`.
- `src/app/palette.js` — the **command palette** (Ctrl+K): the project's chats, the other projects, the actions that can run right now (each runs by clicking the button it stands for, so it inherits that button's guards), and settings. Loose matching (letters in order, case- and diacritic-blind, `paletteMatch`), and with anything typed a last row searching every message (the sidebar search). Tests in `tests/palette.test.js`.
- `src/app/motion.js` + `src/css/motion.css` — the **"Calm+" motion layer**, shared helpers every module may call: press feel (a global pointerdown/up that sinks any button via WAAPI on `scale`, so it never fights a rule's `transition` list), `flipCapture` (rows that change place in a re-rendered list slide there — the sidebar), `glideMark` (one highlight that glides to the open chat), `rollNumber` (odometer counts: tasks badge, bell, git +/−, a fresh reply's Changed-files strip), `flyFromComposer` (a sent message lifts out of the composer into the transcript), and `morphInto` (a View Transition: the clicked project card grows into the chat). The rest lives where it belongs: the typer fades each revealed stretch in (`.tw`) and sweeps a reply that landed, chips draw their check as they finish, `glideFeed` (feed.js) eases the feed after the stream. Every helper checks `motionOK()` and does the plain thing under reduced motion.
- `src/app/light.js` — the **living light** behind the chat (layers in `index.html` `#chat-light`, styles in css/composer.css). No backlight panel and no loop: light answers the turn on screen. A lamp sits behind the line Claude is writing and follows it (rises from the composer on send, faint aperiodic flicker while thinking/working, brightness fed by the characters the typer reveals — `lightWords`); a finished tool lets out one soft sideways **beat** at its chip (`lightBeat`, from `tool_result`); typing warms the floor under the composer (`lightKey`); a turn waiting on a permission prompt turns the lamp **amber and still**; when the turn ends it cools slowly and the rAF loop stops, so a resting chat costs nothing. Hooks are called from `stream.js`, `typer.js` and `composer.js`; the state step (`lightStep`) is pure and tested in `tests/light.test.js`. Gated by Extra effects (`body.fx-on`); under reduced motion it shows the state without flicker, beats or glide.
- `src/app/mascot.js` + `src/css/mascot.css` — **the crystal face** that replaced the box-art K in every logo (sidebar, project picker, onboarding, update; the wordmark now reads KRYSTAL). ## Language & communication
- When developing Krystal in this repo, **reply in English** (match the codebase and README).
- The app UI itself supports **EN + HR**.

## Conventions
- **Frontend stays vanilla JS** — no framework, no bundler. Preserve the single-exe simplicity.
- **Global function names must be unique across `src/app/*.js`** — the scripts share one scope, so a second `function foo` silently replaces the first for every caller (`tests/globals.test.js` checks this).
- **Match the surrounding style**; keep dependencies minimal.
- Keep files cohesive as they are (the `claude/` / `commands/` / `db/` split on the Rust side; the per-concern `src/app/*.js` modules on the frontend). When adding UI, put it in the module that owns that concern rather than growing one file back into a monolith.
- Prefer **small, readable changes** over large refactors.

## Code health (applies to every new feature and fix)
The codebase was cleaned of its god files once; these rules keep it that way. Check new work against them before calling it done.

**Where code goes**
- **One concern per file.** New code goes in the file that owns its concern (see the maps above). If no file owns it, make a new one: a `commands/` or `claude/` file on the Rust side, a `src/app/*.js` module plus its own `src/css/*.css` on the frontend. Don't park it in `mod.rs`, `core.js`, `main.rs` or whichever file happens to be open.
- **Watch the size.** When a file passes **~600 lines**, or picks up a second concern, split it in the same change. Don't leave that for "later". When a function passes **~100 lines** or **7 parameters**, break it up. For a function that threads state through many arguments, bundle that state into a struct (`TurnState`) and give each case its own small handler (`TurnState::route` → `on_…`). For a long argument list, use a request struct with named fields (`TurnRequest`). Lines means code: a file's `mod tests` and pure data (the `i18n.js` dictionary) don't count. Files already past the mark (`messages.js`, `activity.js`, `git.js`, `base.css`, `transcript.css`) get split the next time a change *adds* to them, as the first step of that change.
- **One home per helper.** Search before writing a small utility (`grep` the name and the idea). Rust helpers shared by several modules go in `util.rs`; frontend ones go in `utils.js`. A second copy of `base_name` or `escapeHtml` is a bug waiting to diverge. Never index a mutex-held resource with a raw `.lock().unwrap()` where a helper exists (`AppState::db()`).

**Moving and splitting code safely**
- **Move, don't rewrite.** Moving code and changing code are separate steps, ideally separate commits. Move whole items (a function with its docs, attributes and tests) unchanged, and prove nothing was lost. Compare the old and new lines, or for CSS the old and new text with comments and whitespace stripped.
- **Keep paths stable.** On the Rust side, turn `foo.rs` into `foo/mod.rs` + files, with `pub use` re-exports so callers keep writing `foo::bar`. A helper one file lends a sibling is `pub(super)`, not `pub`. Tests move with the code they test.
- **Keep execution order.** Frontend scripts and stylesheets are order-sensitive: a script's top-level code runs in load order, and stylesheet link order is the cascade. Cut **contiguous** ranges at top-level boundaries (never inside a block, `@media` or comment), and link the new files exactly where the original was. `tests/boot.test.js` must stay green.

**Tests and checks**
- **A change gets a test.** Every restructured or new code path gets a test that exercises it. If nothing covered a path before you touched it, write that test as part of the change (`a_streamed_answer_becomes_text_and_one_chip_per_tool` exists for this reason).
- **Guard what only agrees by convention.** When two places must match and the compiler can't see it (command wiring, EN/HR keys, script/stylesheet links), add a check that reads both sides, like `tests/commands.test.js`, `tests/i18n.test.js` and `tests/boot.test.js` do. **Prove a new check can fail:** break the thing it guards once, see it fail, then put it back.
- **Clippy stays clean.** `cargo clippy` should add no warnings. Silence one with `#[allow]` only for a stated reason in a comment.

**Docs travel with the code**
- A doc comment (`///`) sits **directly** above the item it documents, with no blank line and no other item in between. A section intro that documents nothing in particular is a plain `//` (or `//!` at the top of a file).
- Moving, renaming or splitting a file updates, in the same change, every place that names it: this file's maps, `README.md`'s file table and diagram, `core.js`'s load-order map, `index.html`, and code comments that say "see foo.js". A stale pointer sends the next session to the wrong file.

## Feel, motion & fluidity
**Fluidity is the point of this app.** Every feature should feel satisfying, alive and fluid. That comes from motion that *answers something*, not from more motion. Before shipping any UI, check it against these principles.

**Principles**
1. **Alive means responsive, not looping.** Motion must answer something real: your input, a state change, Claude's actual work. A loop that runs regardless (a breathing glow, a heartbeat on a timer) is a screensaver: within a minute the eye learns it and it becomes wallpaper or an irritant. If an ambient effect is truly needed, its rhythm comes from real data (the typer's reveal rate feeds the chat lamp; a beat fires on a real `tool_result`), and when it needs variation, use aperiodic noise (incommensurate sines), never a visible cycle.
2. **Rest is still.** When nothing is happening, nothing moves, and that is what gives motion its meaning. Stillness is also a signal: a turn waiting on you holds perfectly still (amber), and a finished turn *settles*. rAF loops run only while something is happening and stop at rest.
3. **Local, not global.** Motion happens where the thing happens: at the chip that finished, at the line being written, at the button you pressed. Never animate the whole page for a small event.
4. **Every action gets an immediate response, and every result lands.** A press sinks (motion.js), sending lifts the message out of the composer, a finished chip draws its check, a count rolls to its new value, a reply ends with one soft sweep. Something should change within ~100ms of any input, and completion should be *felt*: small micro-rewards, never a fanfare.
5. **Continuity, no teleports.** Things travel from where they came from: the message flies from the composer, the lamp rises from it, a project card grows into the chat, a re-sorted row slides to its new place. If an element changes place, show the path.
6. **Asymmetric timing.** Catch fast, release slow: respond to input in ~100–200ms, let things settle in ~0.6–2s (the lamp cools like a filament). Short (~.15–.35s) for UI transitions; long, gentle tails only for ambient decay.
7. **Light is a source, never an outline.** No box-shadow halos around panels: a shadow starts at a crisp edge and the eye finds the box. Use edgeless radial falloffs from a believable source, and a fine still grain where dark gradients would band.
8. **Meaning is consistent.** Green = working/alive, amber = needs you, red = failed. Motion and colour carry the same meaning everywhere (sidebar, project cards, bell, light).
9. **Restraint.** Animate **one** property calmly (usually a size/position slide or opacity), not a stack. Never morph **shape** (`border-radius` pill→box) during a size change; let shape snap. Springy/overshoot curves only for tiny accents (a star pop, a press release), plain `ease` for open/close. Rate-limit repeats (parallel results must not stack beats). Low amplitude. When unsure, do less.

**Craft**
- Reuse the shared helpers before inventing: `motion.js` (`motionOK`, press feel, `flipCapture`, `glideMark`, `rollNumber`, `flyFromComposer`, `morphInto`), `light.js`, `replayClass`, `openOverlay`/`closeOverlay`, the `.panel-swap`/`.list-swap` crossfades.
- Animate `transform`/`opacity` only; no layout-thrashing properties per frame; no always-on `backdrop-filter` over animated content.
- The default state is the *resting* state: an animation hook must not change an element's idle size/footprint.
- **Always provide a reduced-motion fallback** (`@media (prefers-reduced-motion: reduce)` / `motionOK()`) that keeps the *information* (state, colour, position) but drops the movement. Ambient touches are also gated on Extra effects (`body.fx-on`).
- Keep the logic of a living effect in a pure, testable step (like `lightStep`) and test its states, including "comes to rest".

**Process for anything that's about feel**
- **Build it straight into the app by default.** Make an artifact/mockup only when the maintainer asks for one. When one is asked for, simulate the *real flow* (e.g. "Play a turn": typing → send → thinking → tools → streaming → done → rest) with toggles per idea and a strength slider, because a static mock can't show whether something responds.
- Start quieter than you think. If a direction is rejected twice, stop iterating on it: step back, research how great products do it, and propose from principles.
- Name the *why* in comments next to the effect (what it answers and why it rests), as `light.js` and `motion.js` do.
