# CLAUDE.md — Krystal

## Overview
- **Krystal** is a native Windows desktop chat application for **Claude Code** — it wraps the `claude` CLI in a clean graphical UI so users get a proper app experience instead of the terminal.
- **Stack:** Tauri 2 — Rust backend in `src-tauri/` + vanilla HTML/CSS/JS frontend in `src/`. No framework, no bundler.
- **Audience/goal:** make Claude Code pleasant for everyone, including non-technical users. Originally single-purpose; now being generalized to support **any** project type (writing / research / code / data).
- **Status:** functional and shipping at **v0.3.0**; releases automated via GitHub Actions.

## Architecture (keep this split)
- `src-tauri/claude.rs` — builds the CLI invocation and turns its stream-json output into UI events. `base_args` + `apply_mode` + `apply_chat_flags` + `apply_session_flags` assemble the flags: the system prompt spilled to a file, `--effort`, `--fallback-model` (an overloaded model degrades instead of failing the turn), `--autocompact auto`, `--add-dir` for each folder the project has been granted beyond its own, `--mcp-config` for the artifact tool (see `artifacts.rs`; deliberately *not* `--strict-mcp-config`, which would switch off the user's own MCP servers), and in orchestrator mode the worker sub-agents defined inline via `--agents`. `build_prompt` assembles the turn's message: background context (task note, compact seed, #-referenced chats, attached files) leads — **except** when the message opens with `/skill-name`, which the CLI only resolves at the very head of a prompt, so those messages lead and their background follows. `run_turn` drives one turn on a warm session and ends at its `result` event — **unless a background sub-agent is still out** (`BackgroundAgents`): the CLI emits a `result` as soon as Claude says "I'll report back", then wakes itself when the agent finishes and answers again with a second `result`, so the turn is held open until that one. The agent's report arrives as a `task_notification`, not as the result of the call that launched it. `--forward-subagent-text` plus the sub-agent's own `tool_result`s (tagged `parent_tool_use_id`) feed the agent inspector's timeline.
- **Modes** (`models::MODES`, applied by `claude::apply_mode`): **Full access** (id `auto` — what every older chat has stored) keeps `--dangerously-skip-permissions`; **Auto** (id `guarded`) is Claude Code's own `--permission-mode auto`, where a classifier checks each action instead of the user; **Accept edits** (id `edits`) is `acceptEdits`; **Plan** swaps it for `--permission-mode plan`; **Ask** is the terminal's own behaviour — `--permission-mode default` plus `--permission-prompt-tool stdio`, which makes the CLI hand each permission prompt to its *host* instead of refusing (headless, it has nobody else to ask). A prompt arrives as a `control_request`/`can_use_tool` on stdout; `claude::handle_control` parks it on the session and emits a `permission` event, and `commands::answer_permission` writes the `control_response` on stdin (`allow`, `always` = allow and hand the CLI's own `permission_suggestions` back as `updatedPermissions`, or `deny`). The CLI still decides *what* needs asking, so the user's own rules in `.claude/settings*.json` apply as they do in a terminal. Prompts about Krystal's own plumbing — the artifact tool, the task snapshot, saved attachments — are answered by `claude::is_own_business` and never reach the user. Auto and Accept edits get the same host-answered prompt as Ask, for whatever they don't wave through. Ask mode gates each use on a yes; it does **not** curate the toolset.
- `src-tauri/artifacts.rs` — **artifacts**: the self-contained documents Claude builds (a page, a drawing, a report) that open in a panel beside the conversation instead of as a code block inside it. The `claude` binary has no Artifact tool of its own — that is something the *host* application provides — so Krystal hands the session one, over MCP (`--mcp-config`), and it appears in the toolset as `mcp__krystal__artifact`. The MCP server is **this same executable** re-launched with `MCP_FLAG` (`--krystal-mcp-artifacts`), speaking JSON-RPC on stdio; `claude` starts it, Krystal never talks to it. It is the only thing that applies an `old_str`/`new_str` patch, and it writes the resolved document under `KRYSTAL_ARTIFACT_DIR`. Krystal picks the content up from the `tool_use`/`tool_result` events `claude.rs` already parses, so there is one implementation of the patch logic and no IPC bridge to a grandchild process. The content never travels back through the tool's *result* — that would re-inject the whole document into Claude's context on every revision.
- `src-tauri/session.rs` — **persistent per-chat `claude` processes**. A chat is served by one `--input-format stream-json` process: each message is a JSON line on its stdin, so the session id, the loaded context and the prompt cache survive between turns instead of being rebuilt with `--resume` every time. Everything passed as a flag is fixed at spawn, so the flags form the session **key** — changing model/mode/effort/orchestrator (or compacting, clearing, moving the project) retires the process and the next message starts a fresh one. Stop is two-step: the first press is a `control_request`/`interrupt`, not a kill, so a stopped turn keeps its session — but an interrupt is only a *request*, and a turn wedged in a tool run may never honour it, so a second press (or the frontend's escalation timer) makes `stop_chat` retire the session and kill the process tree. An interrupt also never reaches a **background sub-agent**, which lives on in the warm process after its turn ends. So the stdout reader tracks the live agents (`track_agents`), and a stop that finds one goes straight to the kill. `stop_task` does stop a single agent, but the CLI then wakes Claude to answer about it with nobody reading, and that stray `result` would end the chat's next turn early. `Pool` caps warm sessions (`MAX_WARM_SESSIONS`) and retires idle ones (`IDLE_TIMEOUT_SECS`); everything is retired on app exit.
- **Undoing a turn's file changes** (`commands::rewind_files` → `Session::rewind_files`) rides on the CLI's own file checkpointing rather than a snapshot store of ours: sessions are spawned with `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1`, every user message is sent with a `uuid` of our choosing (saved as `messages.ckpt`), and a `control_request`/`rewind_files` naming that uuid puts the project's files back to how they were before that message (`dry_run` only reports). It works on a resumed session too, so a retired process is no obstacle — but checkpoints belong to the session, so a cleared/compacted chat can't be rewound past that point, and only what Claude's *file tools* changed is covered (not a file a shell command rewrote). `commands::session_setup` is the one place a chat's spawn args are built, because those args are the session key and both a turn and a rewind need the same process. The conversation is left alone; `Pool::leave_note` tells Claude on the next message.
- **Per-turn context can't go in the system prompt** — that's fixed at spawn. Anything that varies per turn (today: the task-list note) rides on the user message via `claude::build_prompt`'s `notes` argument.
- `src-tauri/commands.rs` — Tauri command handlers exposed to the frontend. One-off calls whose reply is parsed as JSON (task generation, the Initialize wizard) pin the shape with `--json-schema`; `extract_json` stays as the safety net.
- `src-tauri/db.rs` — SQLite persistence for chats/projects. A turn is written in three beats rather than one, so nothing is lost if the app goes away mid-answer: `begin_turn` saves the user's message *before* Claude is asked anything (and gives an unnamed chat its fallback title there and then), `save_partial` re-writes the answer as it streams (throttled by `claude::PARTIAL_SAVE_MS`), and `finish_turn` completes those same rows and rolls up the totals. A turn that produced nothing (stopped early, session refused to start) ends at `abort_turn`, which keeps the message and drops the empty answer. Rows carry a `partial` flag while the turn is in flight — one left set is a turn the app never finished, and the UI badges it as interrupted.
- `src-tauri/server.rs` — **phone access**: an opt-in HTTP/SSE server on the LAN (hyper, `0.0.0.0:7420`) that serves the touch UI embedded from `src-tauri/src/webui/` and fronts the *same* command functions the window invokes — so a phone is a second view of one app, not a second app. A six-digit PIN (new per start, ten wrong guesses and it locks) is traded for a bearer token; only the shell is public. A turn streams back as SSE by handing `commands::chat` a `Channel::new` whose handler writes into the response body, and the same events are mirrored to the desktop window (`remote-turn-start`/`remote-turn`) so an open chat paints a phone turn live. Generic over the Tauri runtime so the whole server can be stood up against a mock app in its tests. Also here: the **firewall check** (`firewall_status`/`firewall_allow`) — loopback is never filtered, so a Windows Firewall that drops every packet from the phone leaves the host looking perfectly healthy and tells no one. `netsh` is asked whether any inbound rule names this exe (paths aren't localised, so searching the dump works in any Windows language), and the Remote panel's firewall row offers to add one: an elevated helper `.ps1` (UTF-8 **with BOM**, or PowerShell 5.1 reads it as the system codepage) writes a program-scoped `profile=any` rule through a single UAC prompt. The exe path is what a rule is keyed by, so a dev build being allowed says nothing about the installed one.
- `src/app/` — the frontend UI logic, split into cohesive **classic scripts that share one global scope** (no bundler/modules). They load in order via `<script defer>` (see `index.html`); a symbol declared in an earlier file is visible to all later ones, so **load order matters** and `boot.js` (the entry point) loads last. Layout: `core` (IPC/`els`/`state`/`api`/utils) → `icons` → `motion` → `light` → `sidebar` → `chat` → `projects` → `controls` → `activity` → `agents` → `search` → `messages` → `review` → `artifacts` → `stream` → `permissions` → `mentions` → `skills` → `attachments` → `queue` → `wizard` → `localization` → `settings` → `header` → `git` → `links` → `logo` → `usage` → `notifications` → `palette` → `hotkeys` → `boot`. See `src/app/core.js` for the full map.
- `src/i18n.js`, `src/onboarding.js`, `src/updater.js` — i18n dictionary, first-run onboarding, and self-update (load before the `app/` modules).
- Self-updates ship via **GitHub Releases**.

## Frontend file map (where to find things)
Loaded in this order; each file may use symbols from any earlier one (shared global scope).
- `src/i18n.js` — EN/HR string dictionary + `window.I18N` (`t`/`getLang`/`setLang`); fires `i18n:changed`.
- `src/onboarding.js` — first-run gate: install Claude Code + sign-in flow (own IIFE scope).
- `src/updater.js` — self-update overlay (check GitHub Releases, download, install).
- `src/app/core.js` — foundation: Tauri IPC handles, `$`, `tr`, the `els` element map, `state`, context-window constants, the `api` wrapper, and shared utils (`basename`, `escapeHtml`, `closeOverlay`/`openOverlay`, `replayClass`, `cssEsc`, …).
- **Look:** text is Inter, mono (JetBrains Mono) only for what is genuinely technical — code, paths, numbers, the ▸ prompt, the box-art logo. Both ship in `src/fonts/` (SIL OFL, licences alongside) with `@font-face` in `base.css`; nothing is fetched from the network. Surfaces are separated by tone and soft shadow rather than 1px borders; the reading column is `--read-w` (base.css), shared by the transcript and the composer dock. Your messages are compact bubbles on the right; Claude's replies sit on the page with no card.
- `src/app/icons.js` — **the one icon set** (line icons, one stroke weight, `ICON_PATHS`). `icon('name')` gives an inline `<svg class="ui-ico">` for markup built in JS; `data-icon="name"` on any element draws the same icon as a CSS mask in its `::before` — for elements whose text `data-i18n` rewrites (that would wipe an inline svg). The mask rules are generated from the same paths at load. **No emoji in the UI** (Windows draws them in its own style); tips take an icon *name* (`showTip({ icon: 'alert' })`, rendered through `iconOrText`).
- `src/app/header.js` — the chat header's **⋯ menu** (Edit instructions, Settings, Language) and the **context ring** at the end of the dock's tools: `updateUsage` (chat.js) fills the same `#meter-fill`/`#meter-label` — now inside the ring's popover, with the usage chip — and calls `paintContextRing(pct, level)`.
- `src/app/palette.js` — the **command palette** (Ctrl+K): the project's chats, the other projects, the actions that can run right now (each runs by clicking the button it stands for, so it inherits that button's guards), and settings. Loose matching (letters in order, case- and diacritic-blind, `paletteMatch`), and with anything typed a last row searching every message (the sidebar search). Tests in `tests/palette.test.js`.
- `src/app/motion.js` + `src/motion.css` — the **"Calm+" motion layer**, shared helpers every module may call: press feel (a global pointerdown/up that sinks any button via WAAPI on `scale`, so it never fights a rule's `transition` list), `flipCapture` (rows that change place in a re-rendered list slide there — the sidebar), `glideMark` (one highlight that glides to the open chat), `rollNumber` (odometer counts: tasks badge, bell, git +/−, a fresh reply's Changed-files strip), `flyFromComposer` (a sent message lifts out of the composer into the transcript), and `morphInto` (a View Transition: the clicked project card grows into the chat). The rest lives where it belongs: the typer fades each revealed stretch in (`.tw`) and sweeps a reply that landed, chips draw their check as they finish, `glideFeed` (stream.js) eases the feed after the stream. Every helper checks `motionOK()` and does the plain thing under reduced motion.
- `src/app/light.js` — the **living light** behind the chat (layers in `index.html` `#chat-light`, styles in chat.css). No backlight panel and no loop: light answers the turn on screen. A lamp sits behind the line Claude is writing and follows it (rises from the composer on send, faint aperiodic flicker while thinking/working, brightness fed by the characters the typer reveals — `lightWords`); a finished tool lets out one soft sideways **beat** at its chip (`lightBeat`, from `tool_result`); typing warms the floor under the composer (`lightKey`); a turn waiting on a permission prompt turns the lamp **amber and still**; when the turn ends it cools slowly and the rAF loop stops, so a resting chat costs nothing. Hooks are called from `stream.js`; the state step (`lightStep`) is pure and tested in `tests/light.test.js`. Gated by Extra effects (`body.fx-on`); under reduced motion it shows the state without flicker, beats or glide.
- `src/app/sidebar.js` — thread list rendering, inline rename, search/saved results list.
- `src/app/chat.js` — thread view (`openThread`/`showEmpty`), usage meter + context-rot tips, message bubbles (`appendMessage`), star/favorite. `openThread` skips the rows of a turn that is still live (the backend names the first one on a `saved` event, kept as `live.savedFrom`) because the live view paints those itself; a row still flagged `partial` on reload wears an "Interrupted" badge.
- `src/app/projects.js` — project picker (entry screen), `startNewChat`, welcome-screen Initialize/Reinitialize, the **folders panel** (the project path under the chat title opens it: the project folder plus any extra folders granted to it, each passed as `--add-dir`; stored in the SQLite `project_dirs` table and re-keyed by `move_project` like pins), and **change a project's folder** (`moveProjectFolder` → `move_project`: the project keeps its chats/tasks/run command, which the backend re-keys from the old path to the new one; each moved chat's `session_id` is dropped because Claude Code keys its own sessions by working directory).
- `src/app/controls.js` — model/mode/**effort** pickers (`createPicker`), compact/clear/hint actions, the compact/clear progress overlay. Effort is `claude --effort` (low→max, default `high`), remembered per chat like the model and the mode.
- `src/app/activity.js` — Activity panel: live shells & sub-agents (track/render tool runs).
- `src/app/orchestrator.js` / `src/app/agents.js` — orchestrator popover, and the **agent inspector**: a run record per sub-agent (Task) keyed by its `tool_use` id, kept outside `state.live` so a finished agent stays inspectable. Its chip opens a dedicated window with a live step-by-step timeline, token/step/elapsed tiles, the agent's report, and Stop (which ends the owning turn — the CLI can't kill one worker).
- `src/app/search.js` — sidebar search box + Saved (favorites) toggle.
- `src/app/messages.js` — assistant transcript building blocks: action chips (expand/diff/output), plan & AskUserQuestion cards, `renderSegments`.
- `src/app/review.js` — the **Changes panel**: a reply that edited files leaves a strip under it ("Changed files: 3 +12 −4") that opens the files it touched as line diffs, built from the turn's own Edit/Write segments (`turnChanges`, a small LCS `lineDiff`). Click a line to comment; comments collect on the message and go to Claude as **one** message (`reviewMessage`, each quoting its line — an edit carries no line numbers). **Undo** is two-step: a dry run asks what would be touched, then the real thing — see `rewind_files` below.
- `src/app/stream.js` — **desktop notifications** (`notifyAway` → the `notify` command, `tauri-plugin-notification`: a toast when a turn finishes, fails or stops to ask while the window isn't in front; its own switch in Settings), composer input/autosize, the typewriter (`makeTyper`), concurrent per-thread streaming (`state.live`), `send` (takes what's in the composer and either starts a turn or, mid-turn, queues it) / `startTurn` (starts a turn in any chat, on screen or not) / `stopTurn` (first press interrupts and keeps the warm process; pressing stop again — or `STOP_ESCALATE_MS` of nothing happening — escalates to killing it), and the **suggested next message** strip (`--prompt-suggestions` → a `prompt_suggestion` event; it only arrives once a chat has history and only when the CLI has a confident guess, so the strip is a bonus, never a fixture).
- `src/app/permissions.js` — **Ask mode's permission prompt**: the card docked above the composer (not in the transcript — a turn is *waiting* on it, so it must not scroll away, and nothing about it is saved) showing the command or diff being agreed to, with Allow / "always" (worded from the rule the CLI proposed) / Deny. A turn can be waiting on several at once (parallel tool calls, sub-agents), so each liveTurn keeps a queue (`live.permissions`) fed by the `permission`/`permission_gone` events and the card shows the front of it; the sidebar marks a waiting chat in amber and a chat you can't see raises a notification (see `notifications.js`). The phone UI renders the same prompt inline (`webui/app.js`), answering through the command bridge.
- `src/app/notifications.js` — **the bell, toasts, and the project list's live mark**. Anything that happens in a chat that *isn't on screen* — a reply finished (`done`), failed, ended on a question or plan card, stopped on a permission prompt (`ask`), or left its queue on hold — is raised through `notifyChat(live, kind, text)`: a toast slides in under the bell and leaves on its own, and a row stays in the bell's panel until the chat is opened (`openThread` → `dropNotifications`), so the list is only ever what hasn't been looked at. One row per chat; rows persist in localStorage, except `ask`, which no turn outlives. A turn notes its project when it starts (`liveTurnStarted` → `live.cwd`/`live.title`), because it may end after you've left that project and `state.threads` no longer has the chat — that same note is what `paintProjectActivity` reads to mark the project cards with a turn in flight (amber when one waits on a permission prompt). `openNotification` enters the chat's project first if it isn't the open one. The bell is a class (`.notif-toggle`, like the gear) so it can sit both on the project screen and in the chat header; toasts have their own switch (`toasts`) in Settings — the bell collects either way.
- `src/app/hotkeys.js` — **keyboard shortcuts** and the **chat visit history** behind them. Every chat `openThread` puts on screen is noted (`noteChatVisit`) in one browser-style history, across projects: Ctrl+Q/Ctrl+E (and the mouse's side buttons) step back and forward through it, Ctrl+Tab hops to the chat before this one (pressed again, it comes back), Ctrl+W goes to the project list, Ctrl+N starts a new chat, Ctrl+K opens the command palette (`palette.js`), Ctrl+S opens Settings → Shortcuts (`renderShortcutsPanel`). All are Ctrl + a left-hand key, matched by physical key (`e.code`) so they sit in the same place on any layout — chosen for one-handed use on a 60% keyboard with no arrows. An entry keeps its project, so a step can `enterProject` first; a chat that's since been deleted is dropped and the step carries on past it. Persisted in localStorage. Shortcuts stand down while any dialog is open.
- `src/app/mentions.js` — `#`-reference another chat from the composer: a `#` autocomplete over the project's chats, reference pills above the input, and `composerRefsIn` → the references still named in the text, whose thread ids are passed as `refs` to the `chat` command (backend folds the referenced transcripts into the prompt as background context).
- `src/app/skills.js` — the **`/` picker**: type `/` at the head of a message to pick a Claude Code skill (`/code-review`, `/run`, a `.claude/skills` or `.claude/commands` entry of your own). Skills always worked in Krystal — nothing listed them. The list is merged from two halves: the backend scans the project's and the user's `.claude/skills`/`.claude/commands` for names *and descriptions* (`list_skills` → `skills.rs`), while the CLI names its own built-ins — which live inside the binary, not on disk — in every session's `system.init` event, forwarded on the `start` event and cached per project in localStorage. Blurbs for known built-ins live in `i18n.js` (`skillBlurb.*`); an unrecognised skill just shows its name.
- `src/app/attachments.js` — attach files by **paste or drag-and-drop** (no upload button): Ctrl+V a clipboard image (persisted to `<app_data_dir>/attachments/` via the `save_attachment` backend command) or drop files onto the window (Tauri drag-drop event → real paths). Queued as pills above the input; on send their paths ride along as `files` to the `chat` command (backend's `build_prompt` tells Claude to Read them — Claude Code reads images natively). Image chips get a thumbnail via `read_image`.
- `src/app/queue.js` — **queued messages**: a message sent while the chat's turn is still running waits in a strip above the composer (each row can be edited back into the box or dropped) and goes out when that turn finishes — one per turn, in order, whether or not the chat is on screen. Frontend-only: the backend still sees one ordinary `chat` call per message, started from `finishLive` → `queueTurnEnded` → `startTurn`. Queues are per chat and persisted in localStorage like drafts. Only a turn that *finished* pulls the next message; one that was stopped or failed leaves the queue **on hold** (a queue with no turn running — nothing stores that state) with a "Send now" button, and a notification if the chat isn't on screen. Mid-turn the send button is Stop, so a separate queue button appears beside it once something is typed. Because the next turn starts on `done`, the backend folds the turn's task-snapshot edits and artifacts into SQLite *before* emitting `done` (see `chat` in `commands.rs`).
- `src/app/wizard.js` — Initialize wizard state machine (brief → analyze → questions → review → save) + the CLAUDE.md editor.
- `src/app/localization.js` — EN/HR flag toggle; re-renders dynamic surfaces on language change.
- `src/app/settings.js` — Discord presence + the Settings modal (tabs, feature switches, persisted in localStorage). `openSettings(tab)` can open straight onto one tab.
- `src/app/phone.js` — the **Phone** button + Settings → Phone panel (start/stop, the address and pairing code), and the **mirroring** of a turn started on the phone: it builds the liveTurn `send()` would have built and replays the backend's forwarded events through `handleLiveEvent`, so the typewriter, Activity panel, sidebar mark and Stop button all behave as if the message had been typed here.
- `src/app/tasks.js` — per-project to-do list: sidebar-foot Tasks button (open-count badge) + Tasks modal (add/rename/complete/delete/clear-done), plus a "generate from a description" flow that may ask clarifying questions then has Claude draft the tasks (`generate_tasks` backend command; stored in the SQLite `tasks` table keyed by project path). During chat, the backend drops a fresh markdown snapshot under `<app_data_dir>/task-lists/<key>.md` and appends a system-prompt note that **names the open tasks** (capped at `TASK_NOTE_TITLES`; their notes, the done items and the `(id:N)` markers stay in the file for Claude to `Read`). The note asks Claude to **keep the list current unasked** — tick a line off in that file as soon as the work finishing it lands. After the turn, on *every* exit path (including a stopped or failed one), `reconcile_task_snapshot` folds the file's edits back into SQLite and emits a `tasks` event that refreshes the badge/panel and shows a side-tip. See `prepare_task_awareness`/`write_task_snapshot`/`reconcile_task_snapshot` in `commands.rs`, with round-trip tests in that file's `mod tests`.
- `src/app/artifacts.js` — the **artifact panel**: the project's artifacts down the left, the chosen one rendered on the right. HTML and SVG run for real inside a `sandbox="allow-scripts"` iframe (no same-origin, so an artifact can be a live interactive page without being able to reach Krystal); markdown renders in the app's own typography. Two ways in: the card an artifact leaves in the transcript (a tool segment carrying `artifact`, rendered via `specialToolCard`) and the Artifacts button in the sidebar foot. A turn is **one version** however many times Claude patches the artifact while working — versions are what the user asked for, not what the tool did — so the panel drops version numbers while a turn is in flight and picks them back up from the DB when it lands (`artifactsTurnEnded`). Stored in the SQLite `artifacts` table keyed by project path and re-keyed by `move_project`, like pins. Save a copy / Open in browser are the sharing story: an artifact is self-contained by construction, so the saved file works anywhere, offline, on its own.
- **Mermaid diagrams** are the one kind stored as something other than what you see: Claude writes mermaid *source* (which lays the diagram out for it — far better than placing SVG shapes by hand), the DB keeps that source so `old_str` patches keep applying, and the frontend renders it to SVG for the panel and for Save / Open in browser. So the file you send someone is a few KB of SVG, not a renderer in a trench coat. `src/vendor/mermaid.min.js` (3.6 MB uncompressed, ~0.8 MB in the installer) is **loaded lazily** by `ensureMermaid()` the first time a diagram is opened — never at boot, never in a session with no diagrams. Known limit: mermaid's default `htmlLabels` puts labels in `<foreignObject>`, which every browser renders but some non-browser SVG tools (Inkscape, Word, GitHub's inline SVG) do not.
- `src/app/pins.js` — **pinned files**: a rail down the right edge of the chat holding files you want to glance at mid-conversation (a task list, a brief). Rests collapsed at low opacity over the gutter — absolutely positioned, so it never takes layout space — opens on hover (one property animates: the chip's `max-width`), and a click reads the file **fresh** into a light overlay (markdown rendered, anything else as plain text). Pins are **per project**, stored in the SQLite `pins` table keyed by project path, and `move_project` rewrites any that lived inside the folder. Backend: `list_pins`/`add_pin`/`remove_pin`/`read_pinned_file` in `commands.rs`.
- `src/app/git.js` — git status line + branch picker (switch/create/fetch/pull/push), and the **GitHub Actions build chip** at the end of that line: a dot + the workflow that matters now (one in flight, else the latest on this branch, else the latest), a popover of recent runs, and a tip when a run seen in flight lands. A run opens in the **run panel** (`openCiRun`): its jobs and steps with timings, refreshed while it is in flight, and for a failure the end of each failed step's log plus **Ask Claude to fix it**, which sends that log as a message. Backend `ci_runs` / `ci_run` ask the GitHub CLI (`gh run list`, `gh run view --json` and `--log-failed`), which already knows the repo and carries the user's sign-in — so no token handling here, and no chip when `gh` is missing or the folder isn't on GitHub. Polled faster while something runs, not at all while the window is hidden; its own switch (`ciStatus`) sits under the git one.

## Feel, motion & fluidity
**Fluidity is the point of this app.** Every feature should feel satisfying, alive and fluid. That comes from motion that *answers something*, not from more motion. Before shipping any UI, check it against these principles.

**Principles**
1. **Alive means responsive, not looping.** Motion must answer something real: your input, a state change, Claude's actual work. A loop that runs regardless (a breathing glow, a heartbeat on a timer) is a screensaver: within a minute the eye learns it and it becomes wallpaper or an irritant. If an ambient effect is truly needed, its rhythm comes from real data (the typer's reveal rate feeds the chat lamp; a beat fires on a real `tool_result`), and when it needs variation, use aperiodic noise (incommensurate sines), never a visible cycle.
2. **Rest is still.** When nothing is happening, nothing moves, and that is what gives motion its meaning. Stillness is also a signal: a turn waiting on you holds perfectly still (amber), and a finished turn *settles*. rAF loops run only while something is happening and stop at rest.
3. **Local, not global.** Motion happens where the thing happens: at the chip that finished, at the line being written, at the button you pressed. Never animate the whole page for a small event.
4. **Every action gets an immediate response, and every result lands.** A press sinks (motion.js), sending lifts the message out of the composer, a finished chip draws its check, a count rolls to its new value, a reply ends with one soft sweep. Something should change within ~100ms of any input, and completion should be *felt*: small micro-rewards, never a fanfare.
5. **Continuity, no teleports.** Things travel from where they came from: the message flies from the composer, the lamp rises from it, a project card grows into the chat, a re-sorted row slides to its new place. If an element changes place, show the path.
6. **Asymmetric timing.** Catch fast, release slow: respond to input in ~100–200ms, let things settle in ~0.6–2s (the lamp cools like a filament). Short (~.15–.35s) for UI transitions; long, gentle tails only for ambient decay.
7. **Light is a source, never an outline.** No box-shadow halos around panels: a shadow starts at a crisp edge and the eye finds the box. Use edgeless radial falloffs from a believable source, and a fine still grain where dark gradients would band.
8. **Meaning is consistent.** Green = working/alive, amber = needs you, red = failed. Motion and colour carry the same meaning everywhere (sidebar, project cards, bell, light).
9. **Restraint.** Animate **one** property calmly (usually a size/position slide or opacity), not a stack. Never morph **shape** (`border-radius` pill→box) during a size change; let shape snap. Springy/overshoot curves only for tiny accents (a star pop, a press release), plain `ease` for open/close. Rate-limit repeats (parallel results must not stack beats). Low amplitude. When unsure, do less.

**Craft**
- Reuse the shared helpers before inventing: `motion.js` (`motionOK`, press feel, `flipCapture`, `glideMark`, `rollNumber`, `flyFromComposer`, `morphInto`), `light.js`, `replayClass`, `openOverlay`/`closeOverlay`, the `.panel-swap`/`.list-swap` crossfades.
- Animate `transform`/`opacity` only; no layout-thrashing properties per frame; no always-on `backdrop-filter` over animated content.
- The default state is the *resting* state: an animation hook must not change an element's idle size/footprint.
- **Always provide a reduced-motion fallback** (`@media (prefers-reduced-motion: reduce)` / `motionOK()`) that keeps the *information* (state, colour, position) but drops the movement. Ambient touches are also gated on Extra effects (`body.fx-on`).
- Keep the logic of a living effect in a pure, testable step (like `lightStep`) and test its states, including "comes to rest".

**Process for anything that's about feel**
- **Prototype first, as an artifact, before touching the app.** Simulate the *real flow* (e.g. "Play a turn": typing → send → thinking → tools → streaming → done → rest) with toggles per idea and a strength slider. A static mock can't show whether something responds, so judge it in motion.
- Start quieter than you think. If a direction is rejected twice, stop iterating on it: step back, research how great products do it, and propose from principles.
- Name the *why* in comments next to the effect (what it answers and why it rests), as `light.js` and `motion.js` do.
